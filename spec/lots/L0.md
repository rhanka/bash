# Lot L0 — Component pipeline and package skeleton

Lot spec for the build lane (Room 2). Sources of authority: `spec/SPEC_EVOL_BASH_SANDBOX.md` ("EVOL":
decisions D2, D3, D16, D17, D18, D24, D26; Annexes A, C, I) and `plan/PLAN_BASH_SANDBOX_V1.md` (lot L0,
sections 5 and 6). This document is sufficient to build the lot; where it and EVOL differ, stop and raise a
spec issue.

- **Size.** 3.5 points. **Builder.** Sonnet 5.5; fallback Gemini 4 Argon. **Review.** Carbon, full review
  of every PR, dispatched on a green `make check`.
- **Branch.** `feat/l0-pipeline`, worktree `tmp/l0-pipeline`.
- **Outcome.** A reproducible pipeline that turns a `no_std` Rust crate into a WASI 0.2 component with
  zero imports, generates dependency-free JavaScript bindings for it, checks eight gates, and packs an
  installable npm tarball. It ends with the Gate L0 go/no-go report.

## 1. Lane rules

1. The worktree contains no reference source (`tmp/refs/`) and no reference package. Do not fetch any.
2. L0 is the only build lot with network access, and only for tool acquisition from the hosts listed in
   section 4. Everything fetched is verified against a recorded hash or lockfile.
3. No dependency in any published manifest. No Python. No Docker. Never write to `/tmp`; use the
   git-ignored `tmp/` of the worktree.
4. Commits through `make commit`, no attribution trailer of any kind. Code, comments and commit messages in
   English.
5. `Cargo.lock` contains workspace packages only. No crate from a registry, including build and dev
   dependencies.

## 2. Scope

In scope:
- Toolchain and tool pins, tool fetching with verification.
- `tools/build.mjs`, `tools/check.mjs`, `tools/transpile.mjs`, `tools/fetch-tools.mjs`.
- The WIT contract files of EVOL Annex A, validated by a tool.
- A **pipeline probe**: a minimal `no_std` component used to prove the link and to exercise every gate
  before the kernel exists. It stays in the repository as the pipeline's self-test.
- The kernel crate as an empty `no_std` library (no behaviour), so that later lots have a place to build.
- Package skeleton, divergence list file, offline `npm pack` test.
- Continuous-integration workflow running `make check`.
- The Gate L0 report.

Out of scope (later lots): any shell behaviour, the memory module (`kernel::mem`, L1a-1), the Annex A
exports and the JS facade (L1b), session drivers and `wac` (L1c), benchmark (L12), `wasm-opt` (decided at
L2; L0 only leaves the hook described in 6.1), the `stpsh` binary (L17a).

`tools/fetch-tools.mjs` contract:
- Reads `tools/pins.json`. Tools directory: `$SENTROPIC_TOOLS_DIR`, default `tmp/tools/` in the worktree.
- For each tool: if `<dir>/<name>-<version>/` exists with a `.verified` marker holding the pinned hash,

- Never executes anything from the archive. Never updates `pins.json` by itself. `--offline` fails instead
  of downloading.
- Prints one line per tool: `tool <name> <version> verified` or the error.

### 5.2 Kernel crate

`#![cfg_attr(target_arch = "wasm32", no_std)]`, no code beyond what is needed to compile on both the
native target and `wasm32-wasip2`. It exports nothing in L0 and is not componentized yet.

### 5.3 Pipeline probe

`probe/`: crate `sentropic-bash-probe`, `crate-type = ["cdylib"]`, `no_std` on wasm, no use of the `alloc`
crate. Its contract, `probe/wit/probe.wit`:

```wit
package sentropic:bash-probe@0.0.0;

world probe {
  export ping: func(x: u32) -> u32;                 // returns x + 1
  export echo-bytes: func(data: list<u8>) -> list<u8>;   // returns the same bytes
  export grow: func(pages: u32) -> u32;              // memory.grow(pages), returns the new size in pages
}
```

The probe needs: a `#[panic_handler]` that executes `core::arch::wasm32::unreachable()`; a bump allocator
over `core::arch::wasm32::memory_grow` used only by `cabi_realloc` (alignment respected, traps on
exhaustion, never returns null); the three exports. `grow` exists so that a test can make memory grow
between two `echo-bytes` calls and prove that the generated JavaScript refreshes its views.

Bindings: generate the Rust export glue with the pinned CLI and commit the output under
`probe/src/bindings/`:

```
wit-bindgen rust probe/wit --world probe --out-dir probe/src/bindings \
  --std-feature --runtime-path crate::rt --bitflags-path crate::rt::bitflags \
  --disable-custom-section-link-helpers
```

Confirm the exact option spelling with `wit-bindgen rust --help`. `crate::rt` is a small module of the
probe that supplies only what the generated code references. `tools/build.mjs --check-bindings`
regenerates into a temporary directory and fails if the committed files differ.

**Fallback (EVOL D16), not a gate failure.** If the generated code cannot compile under `no_std` without a
runtime crate, write the glue by hand for the probe and say so in the report. The canonical-ABI facts
needed for this world: `ping` is a core export taking and returning one `i32`; `echo-bytes` takes
`(ptr: i32, len: i32)` for the list (the caller allocated it through the exported
`cabi_realloc(old_ptr, old_len, align, new_len) -> ptr`) and returns an `i32` pointer to an 8-byte area
holding the result's `(ptr, len)` as two little-endian `i32`; a `cabi_post_echo-bytes(ret_ptr)` export
lets the caller release the result. The exact core export names are whatever makes
`wasm-tools component new` accept the module for this world; use its error messages as the oracle.

## 6. Build pipeline

### 6.1 `tools/build.mjs` contract

`node tools/build.mjs [--component probe|kernel|all] [--out dist] [--check-bindings]`. Default builds
every component listed in `tools/components.json` (L0: the probe only). No interactive input. Exit code 0
on success. Steps for one component `<c>`:

1. `fetch-tools.mjs --offline` check (tools must already be verified).
2. Core module:
   `cargo build --release --target wasm32-wasip2 -p <crate>` with
   `RUSTFLAGS="-C link-self-contained=no -C link-arg=--no-entry -C link-arg=--skip-wit-component
   --remap-path-prefix=<absolute repo root>=."` and `CARGO_TARGET_DIR=<out>/target`.
   Result: `<out>/<c>.core.wasm`, a core module (magic `00 61 73 6d 01 00 00 00`).
3. Hook for a size pass on the core module: if `tools/components.json` sets `"wasmOpt": true` for the
   component, run the pinned `wasm-opt`; in L0 the flag is `false` everywhere and the step is a no-op.
4. Componentization: `wasm-tools component embed <wit dir> --world <world> <core> -o <tmp>` then
   `wasm-tools component new <tmp> -o <out>/<c>.component.wasm`. No adapter argument. Result: a component
   (magic `00 61 73 6d 0d 00 01 00`).
5. `wasm-tools validate <out>/<c>.component.wasm`.
6. JavaScript bindings: `node tools/transpile.mjs <out>/<c>.component.wasm <out>/js/<c>/` (6.3).
7. Print, per artefact: path, size in bytes, SHA-256.

The build must not depend on the absolute path of the worktree, the user name, the time or the locale.

### 6.2 Link proof (first task of the lot)

Before anything else, prove steps 2 and 4 on the probe. Record in the report, for each attempt: the exact
command, whether it linked, and the output of `wasm-tools component wit` on the result. The proof holds
when the component's printed world has **no `import` line** and the core module has no import section
entry (`wasm-tools print` shows no `(import`).

If the first attempt fails, try these variations one at a time and record each result; they are allowed
because they do not change the target or add a dependency:
- with and without `-C link-self-contained=no`;
- `-C link-arg=--no-entry` replaced by `#![no_main]` plus an explicit exported symbol;
- letting the bundled linker componentize directly (drop `--skip-wit-component`, pass
  `-C link-arg=--component-type=<wit file>` and `-C link-arg=--wasi-adapter=none`), then inspecting the
  result with `wasm-tools component wit`;
- `crate-type = ["cdylib"]` versus `["staticlib"]` followed by an explicit `wasm-ld` step using the
  toolchain's own `wasm-ld`.

Not allowed: another target, a crate, a nightly toolchain, or stubbing WASI imports. If no variation
yields a zero-import component, the gate fails (section 11).

### 6.3 `tools/transpile.mjs` contract

Uses the programmatic `transpile` function exported by `@bytecodealliance/jco-transpile` (loaded from the
staged tools directory). Options, to be matched against the package's type declarations: synchronous
instantiation mode; base64 cutoff 0 so that the core module is written as a separate `.wasm` file; valid
lifting optimization on; top-level-await compatibility off; minification off; no import map. Writes into
the output directory: one JavaScript module, its `.d.ts` files, exactly one core `.wasm`.

The generated module must export an `instantiate(getCoreModule, imports)` function that is synchronous
when `getCoreModule` is. It must contain no top-level `await`.

## 7. Gates and `tools/check.mjs`

`node tools/check.mjs [--quick] [--only G<k>]` runs, in order, and prints one line per gate
(`G1 zero-import: OK` or `G1 zero-import: FAIL <reason>`), exit code 1 if any gate fails:

| Gate | Executable definition |
|---|---|
| G1 zero import | For every built component: `wasm-tools component wit <component>`; fail if the printed world contains a line starting with `import` |
| G2 no bare import | For every `.js` file under `<out>/js/` and `host/`: extract static `import`/`export ... from` specifiers and `import()` string literals; fail if a specifier does not start with `./` or `../`, except `node:` specifiers in files under `host/node/`. Follow the import graph from `host/browser.js`: fail if it reaches any `node:` specifier, `process.getBuiltinModule` or `createRequire`. Fail on `import()` with a non-literal argument |
| G3 two-build identity | Copy the tracked files (`git ls-files`) into two different directories under `tmp/`, run the build in each, fail if any `*.core.wasm`, `*.component.wasm` or file under `js/` differs in SHA-256. Skipped under `--quick`, printed as `G3 two-build identity: SKIPPED (quick)` |
| G4 component validity | `wasm-tools validate`; then the WIT printed from the component equals the committed WIT for its world after normalization through `wasm-tools component wit` |
| G5 one core module | Under each `<out>/js/<c>/`: exactly one `.wasm` file; no `.js` file contains a base64 literal longer than 1 000 characters |
| G6 zero crate, heap discipline | Every `[[package]]` in `Cargo.lock` is a workspace member; in `kernel/src/`, no `use alloc::{vec, string, collections, boxed, rc, fmt}` or `alloc::borrow::ToOwned` outside `kernel/src/mem/` and `kernel/src/bindings/` (both may be absent in L0). The probe is exempt because it must not use the `alloc` crate at all, which the gate also checks |
| G7 manifests | The existing `check-attribution`, `check-no-python`, `check-no-deps`; plus: root `package.json` has no `dependencies`, `peerDependencies`, `optionalDependencies` entries and no `preinstall`/`install`/`postinstall`/`prepare` script |
| G8 tool pins | Every tool of `tools/pins.json` has its `.verified` marker with the pinned hash; `<tools dir>/npm/package-lock.json` is byte-identical to `tools/package-lock.json`; no `node_modules` directory exists in the repository outside `tmp/` |

After the gates, `check.mjs` runs `node --test test/`.

Makefile after this lot: `build` runs `node tools/build.mjs`; `test` runs build then `node --test test/`;
`check` runs the three existing checks, the build, then `node tools/check.mjs`; `check-quick` passes
`--quick`; `bench` unchanged. `make check` on a fresh clone must work after `node tools/fetch-tools.mjs`.

## 8. Package skeleton

`package.json` changes (name, version, license, `type`, empty dependency objects unchanged; `private`
stays `true`, publication is a later decision):

```json
{
  "engines": { "node": ">=22.12" },
  "exports": {
    ".": { "types": "./types/index.d.ts", "default": "./host/index.js" },
    "./browser": { "types": "./types/browser.d.ts", "default": "./host/browser.js" }
  },
  "files": ["host/", "types/", "wit/", "dist/js/", "dist/*.component.wasm", "DIVERGENCES.md"]
}
```

- `host/index.js` and `host/browser.js` are placeholders in L0: each exports one function
  `pipelineProbe()` that loads the probe's generated bindings and returns its exports. `host/index.js`
  reads the core module with `readFileSync(new URL(...))` from a file under `host/node/` and compiles it
  synchronously; `host/browser.js` takes a compiled `WebAssembly.Module` as argument and imports nothing
  from `node:`. They are replaced by the real facade in L1b; the entry names stay.
- The package must load with both `import` and `require` on the supported node range (a test covers both).
  If `require` of the ES module fails, add a `require` condition pointing to a small CommonJS wrapper and
  note it in the report.
- `DIVERGENCES.md`: the table of EVOL Annex I (rows V1 to V6 and V8), copied as it stands, with one
  introductory sentence.
- `.gitignore` keeps ignoring `dist/` and `*.wasm`; the `files` list is what puts built artefacts in the
  tarball.

## 11. Exit criteria and the Gate L0 procedure

Exit criteria (all observable):
1. On a fresh clone: `node tools/fetch-tools.mjs && make check` exits 0, with G1 to G8 printed `OK`.
2. `wasm-tools component wit wit/` accepts the Annex A contract (or the report lists the syntax fixes).
3. The five test files pass.
4. `make check` passes twice in a row from two different worktree paths with identical artefact hashes
   (this is G3; state the hashes in the report).
5. The CI workflow is green on the pull request.
6. The report below is committed and reviewed.

**Gate L0 report**, committed as `plan/reports/GATE_L0.md` (add this path to the allowed paths), with:
- toolchain and tool versions actually used, with hashes;
- the link proof of 6.2: commands, outcome of each attempt, the retained recipe;
- the printed world of the probe component (showing no import) and the import section check of its core
  module;
- whether the generated bindings were used or the hand-written fallback, and why;
- whether `jco-transpile` alone was sufficient, and the list of files it produced;
- sizes: probe core module, probe component, generated JavaScript (raw and gzip);
- the result of the Annex A validation;
- the eight gate lines and the artefact hashes of two builds;
- deviations from this spec, each with its reason;
- open risks for L1a-1, L1b and L2.

**Decision.**
- **Go**: criteria 1 to 6 hold and the link proof yields a zero-import component from a `no_std` crate on
  `wasm32-wasip2`. The conductor then opens L1a-1 and L10a.
- **Go with fallback**: as above but with hand-written bindings glue, or with the full `jco` CLI instead
  of `jco-transpile`. Not a failure; the design lane updates the specs of L1b accordingly before it starts.
- **No-go**: no allowed variation of 6.2 produces a zero-import component, or the generated JavaScript
  cannot be made free of bare imports. Stop: commit the report with the evidence, do not start any other
  lot, do not switch target and do not stub imports. The question returns to the owner through the
  conductor, because the only known alternative conflicts with the decision that fixed the target.

## 12. Points the builder must confirm and report

These are stated from tool documentation and package declarations, not from a run on this machine:

# Lot L1a-2 — Memory module completion

Lot spec for the build lane (Room 2). Sources of authority: `spec/SPEC_EVOL_BASH_SANDBOX.md` ("EVOL":
decisions D6, D7, D8; Annex B) and `plan/PLAN_BASH_SANDBOX_V1.md` (lot L1a-2). It completes the module
specified in `spec/lots/L1a-1.md`: **every signature and every behaviour stated there stays as it is**;
this lot replaces implementations and adds items. It runs beside lot L1b and must not require a change in
it. Where this document and EVOL differ, stop and raise a spec issue.

- **Size.** 4 points. **Builder.** Sonnet 5.5; fallback Gemini 4 Argon. **Review.** Carbon, full review of
  every PR, dispatched on a green `make check`.
- **Branch.** `feat/l1a2-mem-allocator`, worktree `tmp/l1a2-mem-allocator`.
- **Outcome.** A production allocator for the wasm target with a bounded footprint, complete byte
  accounting (budgets, ceiling, headroom, reserve), and the three containers later lots need: a scalable
  ordered map, an insertion-ordered map and chunked byte storage.

## 3. Decisions fixed by this spec

| Topic | Decision |
|---|---|
| Weak references | **Not added.** L1b needs none (`spec/lots/L1b.md`, section 4): a child fiber holds a `Budget`, and filesystem mounts are strong references with cycles rejected |
| `KMap` implementation | **B-tree**, node capacity 16 entries, nodes allocated through the map's budget. The sorted vector of L1a-1 is replaced; the interface is unchanged. Reason: maps reach 1 000 000 entries (array and traversal limits of EVOL Annex B) and a sorted vector makes inserts quadratic |
| Hash tables | **None.** Keys come from untrusted scripts; an ordered tree has no collision attack and needs no seed |
| Insertion-ordered map | **Added** (`KInsertMap`, section 5.2): shell variables and associative arrays iterate in insertion order |
| Large byte data | **Added** (`KChunks`, section 5.3): files, output buffers and pipeline data never live in one contiguous growing block |

## 4. Allocator (wasm target)

Replaces the bump allocator behind the ceiling wrapper of L1a-1. The native target keeps the system
allocator behind the same wrapper.

Requirements:
1. General-purpose `alloc`, `dealloc`, `realloc` for any size and any power-of-two alignment up to 16
   (larger alignments may be refused with null).
2. Freed blocks are reused; adjacent free blocks are merged; `realloc` grows or shrinks in place when
   the neighbouring space allows it. Large growth requests may reserve a rounded payload capacity
   for later growth. The exact size is used if rounding would lose an in-place fit or cause refusal.
3. Returns null instead of trapping, for any reason (ceiling, engine refusing `memory.grow`, overflow).
4. Linear memory is grown in steps of at least 64 KiB and at most one eighth of the current footprint
   (minimum step 64 KiB), and only when no free block fits.
5. **Footprint**: the bytes of linear memory the allocator manages. `footprint()` (5.1) reports it. The
   ceiling bounds the footprint: a growth that would take it above the ceiling is refused. `usage().used`
   keeps its L1a-1 meaning (live bytes) and is always at most the footprint.
6. **Reserve**: the allocator sets aside its first 64 KiB page in a separate arena that ordinary
   allocations cannot use. It is available in `reserve_scope` (5.1) even if the ordinary arena is
   fragmented or the engine refuses to grow. A fiber that hit a limit can use it to build its result
   (message, exit code).
7. At most 16 bytes of metadata per live block, excluding alignment and minimum-size rounding.
   Minimum block 32 bytes to hold the header, free-list links and footer when free.
8. Allocation and free of blocks up to 1 KiB are constant-time on average (size-class free lists); the
   stress tests of section 7 give the bound that is checked.
9. No `memory.grow` outside the allocator, anywhere in the kernel.

## 5. Interface additions

All additions are `pub` in `kernel::mem`. Nothing listed in L1a-1 changes.

### 5.1 Accounting

```rust
/// Bytes of memory managed by the allocator (on the native target: equal to usage().used).
pub fn footprint() -> u64;
/// Highest footprint since start.
pub fn footprint_high_water() -> u64;

/// Sets the cap of the transfer account (canonical-ABI buffers). Default: one eighth of the ceiling,
/// recomputed when the ceiling changes unless this function was called. Never lowers below current use.
pub fn set_headroom(bytes: u64) -> Result<(), ConfigError>;
/// The transfer account: limit id LimitId::HEADROOM.
pub fn headroom() -> Budget;

/// Runs `f` with access to the allocator's reserve. Not re-entrant: a nested call runs `f` without
/// further effect. Meant for the short path that reports a limit result.
pub fn reserve_scope<R>(f: impl FnOnce() -> R) -> R;
```

`cabi_realloc` now charges the transfer account for the bytes it hands out and `transfer_free` releases
them. When the account or the allocator refuses, `cabi_realloc` traps as before (it has no error
channel); drivers keep that path unreachable by checking sizes before a call.

### 5.2 `KInsertMap`

```rust
/// Map that iterates in insertion order. Lookup, insert and remove are O(log n).
/// Overwriting an existing key keeps its original position. Removal leaves no gap in iteration.
pub struct KInsertMap<K: Ord + TryClone, V> { /* private */ }
impl<K: Ord + TryClone, V> KInsertMap<K, V> {
    pub fn new_in(budget: &Budget) -> KInsertMap<K, V>;
    /// Returns the previous value. On failure the map is unchanged; key and value are dropped.
    pub fn try_insert(&mut self, key: K, value: V) -> MemResult<Option<V>>;
    pub fn get<Q: Ord + ?Sized>(&self, key: &Q) -> Option<&V> where K: core::borrow::Borrow<Q>;
    pub fn get_mut<Q: Ord + ?Sized>(&mut self, key: &Q) -> Option<&mut V> where K: core::borrow::Borrow<Q>;
    pub fn contains_key<Q: Ord + ?Sized>(&self, key: &Q) -> bool where K: core::borrow::Borrow<Q>;
    pub fn remove<Q: Ord + ?Sized>(&mut self, key: &Q) -> Option<V> where K: core::borrow::Borrow<Q>;
    pub fn len(&self) -> usize;
    pub fn is_empty(&self) -> bool;
    pub fn clear(&mut self);
    pub fn iter(&self) -> impl Iterator<Item = (&K, &V)>;          // insertion order
    pub fn iter_mut(&mut self) -> impl Iterator<Item = (&K, &mut V)>;
    pub fn keys(&self) -> impl Iterator<Item = &K>;
    pub fn values(&self) -> impl Iterator<Item = &V>;
    pub fn budget(&self) -> &Budget;
}
// Also: TryClone where V: TryClone, Drop, Debug.
```

Removed entries may be kept as tombstones internally, but the structure compacts itself so that memory
in use stays within twice what the live entries need, and `iter` never costs more than O(len + removed
since the last compaction).

### 5.3 `KChunks`

```rust
/// Growable byte sequence stored in chunks; never reallocates existing data.
pub struct KChunks { /* private */ }
impl KChunks {
    pub const CHUNK: usize = 65_536;
    pub fn new_in(budget: &Budget) -> KChunks;
    pub fn len(&self) -> u64;
    pub fn is_empty(&self) -> bool;
    pub fn try_append(&mut self, data: &[u8]) -> MemResult<()>;
    /// Writes at `offset`, extending with zero bytes if `offset` is past the end.
    pub fn try_write_at(&mut self, offset: u64, data: &[u8]) -> MemResult<()>;
    /// Copies up to `out.len()` bytes starting at `offset`; returns the count (0 at or past the end).
    pub fn read_at(&self, offset: u64, out: &mut [u8]) -> usize;
    pub fn truncate(&mut self, len: u64);
    pub fn clear(&mut self);
    /// Removes up to `max` bytes from the front, passing them to `sink` in order, slice by slice.
    /// Returns the number of bytes removed. Memory of fully consumed chunks is released.
    pub fn drain_front(&mut self, max: usize, sink: impl FnMut(&[u8])) -> usize;
    /// The stored bytes as consecutive slices.
    pub fn chunks(&self) -> impl Iterator<Item = &[u8]>;
    pub fn budget(&self) -> &Budget;
}
// Also: TryClone, Drop, Debug (length only).
```

Rules: a failed `try_append` or `try_write_at` leaves the content unchanged. The budget is charged for
the bytes of chunk storage actually allocated. A sequence shorter than one chunk allocates a block sized
to its content rounded up to the next power of two (minimum 64 bytes), so that small files do not cost a
whole chunk; from one chunk on, storage is a list of full chunks plus one last partial chunk sized the
same way. Memory held is therefore at most `len` rounded up, plus 16 bytes per chunk of bookkeeping.

## 6. `KMap` as a B-tree

Same interface and iteration order as L1a-1. Additional guarantees: insert, lookup and remove are
O(log n); `iter` is O(n); memory charged to the budget is at most 2 times
`len * (size_of::<K>() + size_of::<V>())` plus 64 bytes per node, for any sequence of operations; `clear`
releases everything.

## 7. Tests and exit gates

Native tests under `kernel/tests/` or next to the code. Allocator tests run on the **wasm** build: the
`mem-test-exports` feature exports plain functions (integer arguments and results only, no component
glue) that run a workload inside the module and return measurements; a `node:test` file instantiates
that core module directly with `WebAssembly.Instance` and an empty import object.

Workloads, all driven by a fixed-seed generator inside the module, each reaching a peak of live bytes of
at least 8 MiB:
- **W1 uniform**: 10 000 cycles; each cycle allocates or frees a block of 16 to 4 096 bytes with equal
  probability once the live set holds 4 096 blocks.
- **W2 bimodal**: as W1, starting with 2 000 live blocks, 90% of blocks of 16 to 256 bytes and 10% of
  64 KiB to 1 MiB.
- **W3 growing buffers**: eight buffers grown by `realloc` in steps of 1.5 times from 64 bytes to 8 MiB,
  interleaved round-robin, then freed.
- **W4 sawtooth** (adversarial): allocate 4 096 blocks of 4 KiB, free every other one, allocate 2 048
  blocks of 8 KiB.

Exit gates, all observable:

1. **Footprint bound.** For W1, W2 and W3: `footprint_high_water() <= 1.25 * peak live bytes`. For W4
   the ratio is reported in the PR and must be at most 2.0.
2. **Full return.** After each workload frees everything: `usage().used` equals its value before the
   workload, and one allocation of 99% of the footprint (minus the reserve) succeeds without the
   footprint growing.
3. **Reuse.** Running W1 ten times in a row leaves `footprint_high_water()` unchanged after the first
   run.
4. **Ceiling on footprint.** With the ceiling at C, the footprint never exceeds C in any workload; the
   allocation that would need growth beyond C returns null; after `raise_ceiling` it succeeds.
5. **Null, never trap.** A request of `usize::MAX / 2` bytes, an alignment of 32, and a request with the
   engine's memory maximum reached all return null; the module is still usable afterwards.
6. **Alignment and content.** Blocks requested with alignments 1, 2, 4, 8, 16 are aligned; `realloc`
   preserves content for every pair of sizes in {1, 15, 16, 17, 4 095, 4 096, 65 536, 1 048 576}.
7. **Reserve.** With the heap filled to the ceiling by ordinary allocations, an ordinary 4 KiB allocation
   returns null and the same allocation inside `reserve_scope` succeeds; a nested `reserve_scope` has no
   further effect. This also holds with ordinary memory fragmented and with an engine limit below the
   configured ceiling.
8. **Headroom.** `cabi_realloc` charges `headroom()` and `transfer_free` releases it to exactly its
   previous value; `set_headroom` below current use returns an error; exceeding the account traps on wasm
   (asserted from node as a `WebAssembly.RuntimeError`) and panics natively.
9. **Speed.** On the build machine, W1 completes in less than 50 ms and 1 000 000 allocate/free pairs of
   64 bytes in less than 100 ms, both in the wasm build under node.
10. **`KMap`.** Agrees with a reference model over 200 000 seeded operations (insert, overwrite, lookup,
    remove), iterating in ascending order at every 1 000th step; 1 000 000 inserts of random `u64` keys
    followed by their lookup and removal complete in less than 2 seconds natively in a release build;
    after `clear`, `budget.used()` is 0; the memory bound of section 6 holds at the 1 000 000-entry peak.
11. **`KInsertMap`.** Agrees with a reference model (insertion order, overwrite keeps position, removal
    closes the gap) over 200 000 seeded operations; 1 000 000 inserts then removals in less than 3
    seconds natively; memory bound of 5.2 checked after removing 90% of the entries.
12. **`KChunks`.** Agrees with a plain byte vector model over 20 000 seeded operations (`try_append`,
    `try_write_at` inside, across and past the end, `read_at`, `truncate`, `drain_front`); appending
    100 MiB in 1 MiB steps never allocates a block larger than `CHUNK` and charges at most
    `len + 65 536 + 16 * chunks` bytes; a 10-byte sequence charges at most 64 bytes plus bookkeeping; a
    failed append at the budget leaves length and content unchanged; after `drain_front` of everything,
    `budget.used()` is 0.
13. **L1a-1 gates still pass.** Every exit gate of `spec/lots/L1a-1.md` passes unchanged, including its
    interface test, with the new implementations.
14. **No grow elsewhere.** A source check fails if `memory_grow` appears outside the allocator file.
15. `make check` green on a clean worktree, G1-G8 `OK`; the kernel core module still has zero imports
    and its size is stated in the PR next to the L1a-1 figure.
